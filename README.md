# GMI Trade Memo App

A small Streamlit app that replaces the Qualtrics-based trade memo submission
process for MBA/EMBA GMI. One designated submitter per team fills out and
edits a trade memo as a draft; once they submit final it locks, and only an
end date can be added afterward. Tickers are checked against an instructor-
maintained permitted-instrument list before final submission is allowed.

## How it maps to the current process

| Old process (Qualtrics) | This app |
|---|---|
| Google Form / Qualtrics survey | Streamlit web form (`app.py`) |
| Manual copy into master Blotter tab | `Instructor view -> Download blotter (.xlsx)` produces a file with the same column layout as your existing Blotter tab |
| No ticker validation | Tickers checked against `data/permitted_tickers.csv` before final submit |
| Anyone in the response could edit indefinitely | Only the team holding the shared access code can edit; drafts are freely editable, submitted trades are locked except for end date |
| Email confirmation -> PDF -> Canvas upload | "Download submission confirmation" button produces a text file the student can upload to Canvas instead |

## One-time setup (instructor)

1. **Install dependencies**
   ```bash
   python -m venv .venv && source .venv/bin/activate   # optional but recommended
   pip install -r requirements.txt
   ```

2. **Edit `data/team_roster.csv`** so it has one row per `section,team` for
   the current semester (a starter file with two sections' worth of NATO-
   alphabet team names is already there -- delete/add rows as needed).

3. **Edit `data/permitted_tickers.csv`** to reflect the instruments you want
   to allow this semester. It uses simple wildcard patterns, e.g.:
   ```
   SPY US Equity        # exact match only
   GC* Comdty            # any Gold futures contract month/year
   * Curncy               # any FX pair
   * Index                 # any index
   ```
   Bond/CDS-style tickers (yellow key Corp/Govt/Muni/etc.) are intentionally
   *not* whitelisted here -- there's no way to enumerate every CUSIP a
   student might trade in advance. Those get a "needs review" flag instead
   of being blocked outright, and show up for you in the instructor view.

4. **Generate team access codes:**
   ```bash
   python seed_teams.py
   ```
   This writes `data/team_access_codes.csv`. Distribute each row's code
   *only* to that team's designated submitter (e.g. individual Canvas
   messages or a mail merge) -- do not post the whole list anywhere
   students can see other teams' codes. Re-running the script regenerates
   every code, which is a handy way to lock out a team if the wrong person
   ends up with the code.

5. **Set the instructor code.** Copy `.streamlit/secrets.toml.example` to
   `.streamlit/secrets.toml` and set `INSTRUCTOR_CODE` to something only
   you know. This gates the "Instructor view" page (blotter export, roster
   of submitted trades).

## Running locally

```bash
streamlit run app.py
```
Open the URL it prints (usually `http://localhost:8501`).

## Deploying so students can reach it

The simplest option, since this is a Streamlit app on GitHub:

1. Push this folder to a GitHub repo (`data/trade_memos.db` and
   `data/team_access_codes.csv` are gitignored on purpose -- don't commit
   real student data or access codes to a public repo).
2. Go to [share.streamlit.io](https://share.streamlit.io), sign in, and
   deploy from your repo, with `app.py` as the entry point.
3. In the deployed app's settings -> **Secrets**, paste:
   ```
   INSTRUCTOR_CODE = "your-real-code"
   ```
4. **Important:** Streamlit Community Cloud's filesystem is ephemeral --
   the SQLite file will reset if the app redeploys or sleeps for a long
   time. For a one-semester class this is usually fine if you download the
   blotter export periodically as a backup. If you want durable storage
   across redeploys, swap `db.py`'s `DB_PATH` for a mounted volume or a
   hosted Postgres/Supabase database (the `db.py` module is a thin enough
   wrapper that this is a same-file change plus a different connection
   string).
5. You (or a TA) still need to run `seed_teams.py` once, locally, against
   the same database the deployed app uses, to create the access codes.
   If you move to a hosted database, run it pointed at that database's
   connection string instead of the local SQLite file.

## Student / team workflow

1. Designated submitter goes to the app, picks their section and team, and
   enters the team's access code.
2. They fill out the form (same fields as the old Qualtrics form: submitter
   info, trade title, 1 or 2 legs, tickers, thesis/implementation/scenario
   narrative, limits).
3. **Save draft** any number of times while the trade is still being
   worked out -- fully editable.
4. **Submit final** runs ticker validation and required-field checks. If
   everything passes, the trade locks and a start date is stamped
   automatically.
5. After submission, the only field that can still change is **end date**
   (for closing out the trade later in the semester).
6. A "Download submission confirmation" button produces a text file they
   can upload to Canvas in place of the old email-confirmation PDF.

## Instructor workflow

- **Instructor view** (gated by `INSTRUCTOR_CODE`) shows every team's
  trades and status, and has two download buttons that produce an `.xlsx`
  with the exact same column layout as your current Blotter tab
  (`section, team, start_date, end_date, trade_no, trade_name, total_legs,
  leg_1_direction, leg_1_ticker, leg_1_exp, leg_2_direction, leg_2_ticker,
  sing_leg_take_prof, sing_leg_stop_loss, symmetric_lmt, sym_lmt_take_prof,
  sym_lmt_stop_loss, leg_1_take_prof, let_1_stop_loss, leg_2_take_prof,
  let_2_stop_loss`), so it drops straight into your existing PL-tracking
  workflow.
- Trades flagged `needs_review` (bonds/CDS not on the standing whitelist)
  aren't blocked from submission, but you'll want to eyeball them each week.

## Extending later

- Multiple trade legs beyond 2, or additional asset classes: extend the
  `trades` table in `schema.sql` and the corresponding form fields in
  `app.py`.
- Automated P&L tracking against Bloomberg: this app deliberately does not
  attempt to call the Bloomberg API (not reachable from a student's laptop
  or from Streamlit Cloud). The ticker fields are stored exactly as typed
  so they can be pulled into a separate Bloomberg Terminal/BLPAPI-connected
  script for weekly P&L updates, the same way the current blotter is used.
