# GMI Trade Memo App

A small Streamlit app that replaces the Qualtrics-based trade memo submission
process for MBA/EMBA GMI. One designated submitter per team fills out and
edits a trade memo as a draft; once they submit final it locks, and only an
end date can be added afterward. Tickers are checked against an instructor-
maintained permitted-instrument list before final submission is allowed.

## How it maps to the current process

| Old process (Qualtrics) | This app |
|---|---|
| Google Form / Qualtrics survey | Streamlit web form (`app.py`) |
| Manual copy into master Blotter tab | `Instructor view -> Download blotter (.xlsx)` produces a file with the same column layout as your existing Blotter tab |
| No ticker validation | Tickers checked against `data/permitted_tickers.csv` before final submit |
| Anyone in the response could edit indefinitely | Only the team holding the shared access code can edit; drafts are freely editable, submitted trades are locked except for end date |
| Email confirmation -> PDF -> Canvas upload | "Download submission confirmation" button produces a text file the student can upload to Canvas instead |

## Project layout

## One-time setup (instructor)

1. **Install dependencies**
   ```bash
   python -m venv .venv && source .venv/bin/activate   # optional but recommended
   pip install -r requirements.txt
   ```

2. **Edit `data/team_roster.csv`** so it has one row per `section,team` for
   the current semester (a starter file with two sections' worth of NATO-
   alphabet team names is already there -- delete/add rows as needed).

3. **Edit `data/permitted_tickers.csv`** to reflect the instruments you want
   to allow this semester. It uses simple wildcard patterns, e.g.:
   ```
   SPY US Equity        # exact match only
   GC* Comdty            # any Gold futures contract month/year
   * Curncy               # any FX pair
   * Index                 # any index
   ```
   Bond/CDS-style tickers (yellow key Corp/Govt/Muni/etc.) are intentionally
   *not* whitelisted here -- there's no way to enumerate every CUSIP a
   student might trade in advance. Those get a "needs review" flag instead
   of being blocked outright, and show up for you in the instructor view.

4. **Set up durable storage (Supabase Postgres) -- do this before you seed
   teams or go live.** See "Durable storage: Postgres / Supabase" below.
   Once you have a `DATABASE_URL`, put it in `.streamlit/secrets.toml`
   (copy from `.streamlit/secrets.toml.example`) for local use, and in the
   deployed app's Secrets for production (step 3 under Deploying, below).

5. **Generate team access codes.** Easiest: once the app is running (locally
   or deployed), go to **Instructor view** and click "Generate / regenerate
   all team access codes" -- no terminal needed. (The command-line
   equivalent, `python seed_teams.py`, still works too, and writes
   `data/team_access_codes.csv` locally.) Distribute each row's code
   *only* to that team's designated submitter -- do not post the whole
   list anywhere students can see other teams' codes. Regenerating
   invalidates every existing code, which is a handy way to lock out a
   team if the wrong person ends up with the code -- but do this against
   whichever database (local or Supabase) the students will actually be
   using, since codes aren't shared between the two.

6. **Set the instructor code.** In the same `secrets.toml`, set
   `INSTRUCTOR_CODE` to something only you know. This gates the
   "Instructor view" page (blotter export, roster of submitted trades,
   team code generation).

## Durable storage: Postgres / Supabase

By default (no `DATABASE_URL` configured), the app stores everything in a
local SQLite file. That's fine for trying the app out on your own laptop,
but Streamlit Community Cloud's filesystem is ephemeral -- a SQLite file
living only in the deployed container can be lost when the app redeploys,
sleeps and wakes, or restarts. For a real semester's worth of student
submissions, point the app at a small hosted Postgres database instead;
this is a five-minute one-time setup and needs no code changes.

1. Go to [supabase.com](https://supabase.com) and create a free account
   and a new project (pick any name/region; the free tier is more than
   enough for this app's traffic).
2. In your project, go to **Project Settings -> Database -> Connection
   string**, choose the **URI** tab, and copy it. It looks like:
   ```
   postgresql://postgres:[YOUR-PASSWORD]@[YOUR-PROJECT-REF].supabase.co:5432/postgres
   ```
   (Supabase shows a placeholder for the password if you didn't set one
   when creating the project -- there's a "reset database password" link
   on that same page if you need it.)
3. Put that full string in `DATABASE_URL`:
   - **Locally:** in `.streamlit/secrets.toml` (copy from
     `.streamlit/secrets.toml.example` and fill in both `INSTRUCTOR_CODE`
     and `DATABASE_URL`).
   - **Deployed:** in the app's Settings -> Secrets on Streamlit Community
     Cloud, alongside `INSTRUCTOR_CODE`.
4. That's it -- the next time the app runs (locally or deployed), it
   detects `DATABASE_URL` and automatically uses Supabase instead of
   SQLite, creating the tables on first run. You don't need to run any
   separate migration step.

Because this is a real hosted database rather than the app container's own
disk, it survives redeploys, sleep/wake cycles, and even switching which
platform hosts the app in the future. It's also the *same* database
whether you're running the app locally or it's deployed on Streamlit Cloud
-- so testing locally against `DATABASE_URL` will show you real,
live student data. Be mindful of that when poking around for testing
purposes once the semester is underway.

**Optional but recommended:** keep the app from going to sleep in the
first place (separately from the storage question) by pointing a free
uptime monitor -- e.g. [UptimeRobot](https://uptimerobot.com) or
[cron-job.org](https://cron-job.org) -- at your deployed app's URL every
6-8 hours. Community Cloud puts apps with no visitor traffic to sleep
after about 12 hours; a sleeping app isn't deleted, and now that data
lives in Supabase nothing is lost either way, but this avoids students
seeing the "app is sleeping" wake-up screen.

## Running locally

```bash
streamlit run app.py
```
Open the URL it prints (usually `http://localhost:8501`). If
`DATABASE_URL` is set in `.streamlit/secrets.toml`, this connects to the
same Supabase database the deployed app uses; if not, it uses a local
SQLite file at `data/trade_memos.db` (gitignored).

## Deploying so students can reach it

1. Push this folder to a GitHub repo (`data/trade_memos.db` and
   `data/team_access_codes.csv` are gitignored on purpose -- don't commit
   real student data or access codes to a public repo; with Supabase
   configured, `trade_memos.db` won't even be created).
2. Go to [share.streamlit.io](https://share.streamlit.io), sign in, and
   deploy from your repo, with `app.py` as the entry point.
3. In the deployed app's settings -> **Secrets**, paste:
   ```
   INSTRUCTOR_CODE = "your-real-code"
   DATABASE_URL = "postgresql://postgres:...@....supabase.co:5432/postgres"
   ```
4. Once deployed, open **Instructor view** and generate team access codes
   as described in step 5 of One-time setup, above.

## Student / team workflow

1. Designated submitter goes to the app, picks their section and team, and
   enters the team's access code.
2. They fill out the form (same fields as the old Qualtrics form: submitter
   info, trade title, 1 or 2 legs, tickers, thesis/implementation/scenario
   narrative, limits).
3. **Save draft** any number of times while the trade is still being
   worked out -- fully editable.
4. **Submit final** runs ticker validation and required-field checks. If
   everything passes, the trade locks and a start date is stamped
   automatically.
5. After submission, the only field that can still change is **end date**
   (for closing out the trade later in the semester).
6. A "Download submission confirmation" button produces a text file they
   can upload to Canvas in place of the old email-confirmation PDF.

## Instructor workflow

- **Instructor view** (gated by `INSTRUCTOR_CODE`) shows every team's
  trades and status, and has two download buttons that produce an `.xlsx`
  with the exact same column layout as your current Blotter tab
  (`section, team, start_date, end_date, trade_no, trade_name, total_legs,
  leg_1_direction, leg_1_ticker, leg_1_exp, leg_2_direction, leg_2_ticker,
  sing_leg_take_prof, sing_leg_stop_loss, symmetric_lmt, sym_lmt_take_prof,
  sym_lmt_stop_loss, leg_1_take_prof, let_1_stop_loss, leg_2_take_prof,
  let_2_stop_loss`), so it drops straight into your existing PL-tracking
  workflow.
- Trades flagged `needs_review` (bonds/CDS not on the standing whitelist)
  aren't blocked from submission, but you'll want to eyeball them each week.

## Extending later

- Multiple trade legs beyond 2, or additional asset classes: extend the
  `trades` table in both `schema_sqlite.sql` and `schema_postgres.sql`
  (keep them in sync) and the corresponding form fields in
  `app.py`.
- Automated P&L tracking against Bloomberg: this app deliberately does not
  attempt to call the Bloomberg API (not reachable from a student's laptop
  or from Streamlit Cloud). The ticker fields are stored exactly as typed
  so they can be pulled into a separate Bloomberg Terminal/BLPAPI-connected
  script for weekly P&L updates, the same way the current blotter is used.
